# Prueba 02.6 · Cotizar con `<COBERTURAS>` modificado

**Qué se quiere saber:** si GNP acepta, dentro de un `<PAQUETE>`, un bloque
`<COBERTURAS>` con valores distintos a los del paquete por defecto — y si
tarifica correctamente cuando lo hace.

**Por qué importa:** es la prueba de fuego del módulo Juega y Compara
([ADR-007](./03_Decisiones/ADR-007-modulo-juega-y-compara.md)). Todo el
diseño de plantillas de ese ADR depende de que esto funcione. `cot_opcionales`
existe desde hace tiempo pero nunca se había usado — 0 filas — así que nadie
había probado esto contra el servicio real.

> **Corrió contra PRODUCCIÓN**, el 2026-09-10. `cotizar` no emite póliza, sólo
> tarifica — mismo principio que las demás pruebas de esta carpeta.

---

## Cómo se corrió

Script: [`app/scripts/prueba_coberturas_modificadas.php`](../app/scripts/prueba_coberturas_modificadas.php).

Base — la misma en los cuatro casos, cambia únicamente `<COBERTURAS>`:

| | |
|---|---|
| Vehículo | Honda Fit FUN L4 1.5 AUT 2015 · clavemarca `AUTHO0614` |
| Paquete | Amplia · `PRS0009355` |
| Contratante | Persona física, 50 años, CP 76000 |
| Conductor | 43 años, CP 04200 |
| Procedencia | Residentes (`01`, la única verificada — ADR-005 punto 11) |
| Vigencia | 2026-09-10 a 2027-09-10, anual |

Cada llamada pasó por `GnpClient::cotizar()` y quedó en `sys_llamadas` con
`cotizacion_id NULL`, igual que las llamadas de los scripts de catálogo. No se
tocó `cot_cotizaciones`, `cot_resultados` ni `cot_opcionales` — es una prueba
de protocolo, no una cotización de negocio.

**Nota sobre el Caso 3:** en `cat_coberturas`, las 27 claves de AUTO aparecen
en la matriz de Amplia, Amplia Total, Premium y Auto Elite por igual — sólo
cambia si están marcadas `BASICA` u `OPCIONAL`. Ninguna quedó como "N/A" en
Amplia con los datos ya cargados, así que no existe hoy el caso exacto que
sugiere el ejemplo del ADR-007 ("algo que sólo es Básica en Premium"). Para no
inventar una clave que no existe, el Caso 3 usa una cobertura real de GNP pero
de otro grupo — **Asistencia Vial Moto** (`0000001567`), exclusiva de
motocicletas — sobre el mismo paquete Amplia/AUTO. Prueba lo mismo que se
quería confirmar (¿GNP deja pedir algo fuera de lo que el paquete/tipo de
vehículo ya trae?) sin necesitar un dato que no está en la base.

## Resultados

| Caso | `<COBERTURAS>` enviado | Resultado | `TOTAL_PAGAR` |
|---|---|---|---|
| **00 — Control** | vacío | `200` OK | **8,183.48** |
| **01 — Caso 1** | GMO (`0000000906`) → 300,000 | `200` OK | **8,204.51** |
| **02 — Caso 2** | GMO (`0000000906`) → 250,000 | Rechazada | — |
| **03 — Caso 3** | Asistencia Vial Moto (`0000001567`) en paquete AUTO | Rechazada | — |

### Caso 1 — cambio válido: **`[CONFIRMADO]`**

GNP acepta un `<COBERTURAS>` modificado y tarifica de forma coherente.

- **¿Acepta la modificación?** Sí, HTTP 200 sin `<ERROR>`.
- **¿Cambia `TOTAL_PAGAR` de forma coherente?** Sí: de 8,183.48 (control) a
  8,204.51 con GMO en 300,000 — una diferencia de **+21.03**, consistente con
  subir una suma asegurada de una cobertura básica de bajo monto relativo
  (Gastos Médicos Ocupantes casi no pesa en la prima total de Daños
  Materiales/Robo Total, que son las que dominan el Amplia). No es un salto
  errático ni un cambio nulo.
- **¿La cobertura modificada aparece reflejada en la respuesta?** Sí, textual:

  ```xml
  <COBERTURA>
     <CVE_COBERTURA>0000000906</CVE_COBERTURA>
     <NOMBRE>GASTOS MÉDICOS OCUPANTES</NOMBRE>
     <SUMA_ASEGURADA>$ 300,000</SUMA_ASEGURADA>
     <DEDUCIBLE>No aplica</DEDUCIBLE>
  </COBERTURA>
  ```

**XML de entrada** (contraseña enmascarada, evidencia completa en
`datos/evidencia_02.6_coberturas_modificadas/01-caso1-peticion.txt`):

```xml
<COTIZACION>
   <SOLICITUD>
      <USUARIO>AESPIN870946</USUARIO>
      <PASSWORD>***</PASSWORD>
      <ID_UNIDAD_OPERABLE>NOP0000016</ID_UNIDAD_OPERABLE>
      ...
   </SOLICITUD>
   <VEHICULO>...</VEHICULO>
   <CONTRATANTE>...</CONTRATANTE>
   <CONDUCTOR>...</CONDUCTOR>
   <PAQUETES>
      <PAQUETE>
         <CVE_PAQUETE>PRS0009355</CVE_PAQUETE>
         <DESC_PAQUETE>Amplia</DESC_PAQUETE>
         <COBERTURAS>
            <COBERTURA>
               <CVE_COBERTURA>0000000906</CVE_COBERTURA>
               <NOMBRE>Gastos Médicos Ocupantes</NOMBRE>
               <SUMA_ASEGURADA>300000</SUMA_ASEGURADA>
            </COBERTURA>
         </COBERTURAS>
      </PAQUETE>
   </PAQUETES>
</COTIZACION>
```

Forma usada: `CVE_COBERTURA` + `NOMBRE` + `SUMA_ASEGURADA` — la misma que
`GnpClient` ya usaba para `cot_opcionales` desde antes de esta prueba (código
verificado el 25 de agosto de 2026, según su propio comentario). No hizo falta
tocar `GnpClient.php`: la capacidad ya estaba escrita, sólo nunca se había
ejercitado.

### Caso 2 — combinación inválida a propósito: **`[CONFIRMADO]`**

GNP la rechaza, y con un error identificable — no es un `<e>` genérico:

```xml
<ERROR>
   <DESCRIPCION>La suma asegurada no aplica para la cobertura con clave 0000000906 (122053399).</DESCRIPCION>
   <CLAVE>14</CLAVE>
   <ORIGEN>cotizador-eot</ORIGEN>
   <FECHA>2026-09-10T13:13:35.209-06:00</FECHA>
</ERROR>
```

El mensaje nombra la clave de cobertura exacta y dice con precisión cuál es el
problema (la suma, no la cobertura en sí). Es un error de validación de
negocio, clasificable y mostrable al vendedor tal cual — no algo que haya que
interpretar a ciegas.

### Caso 3 — cobertura fuera del paquete/tipo base: **`[CONFIRMADO]`**

GNP también la rechaza, con un error igual de claro:

```xml
<ERROR>
   <DESCRIPCION>La cobertura no existe. No aplica para este producto. O no es valida para este negocio.</DESCRIPCION>
   <CLAVE>12</CLAVE>
   <ORIGEN>cotizador-eot</ORIGEN>
   <FECHA>2026-09-10T13:13:35.941-06:00</FECHA>
</ERROR>
```

Esto responde el punto 3 del ADR-007: GNP **no** deja pedir, dentro de un
paquete, una cobertura que ese paquete no trae. La decisión de alcance del
ADR-007 punto 3 (ofrecer sólo coberturas que el paquete base ya trae como
Básica u Opcional) queda confirmada como la única opción viable, no sólo como
la más prudente.

Con la salvedad ya anotada arriba: la prueba se hizo cruzando de **tipo de
vehículo** (moto → auto), no de **paquete dentro del mismo tipo** (algo
Básica-en-Premium-N/A-en-Amplia), porque ese segundo caso no existe hoy en los
datos cargados. Es una prueba más fuerte, no más débil, del mismo principio —
pero si en el futuro apareciera una cobertura real que sí sea N/A sólo entre
paquetes del mismo tipo de vehículo, vale la pena repetir la prueba con ese
caso específico para tener el par exacto.

**Hecho — 2026-09-10, ver [`docs/02.10-rc-accidentes-conductor.md`](./02.10-rc-accidentes-conductor.md):**
apareció el par exacto (Accidentes al Conductor, N/A en Responsabilidad Civil,
Opcional en Amplia/Limitada, mismo tipo de vehículo AUT) al cargar la
plantilla "Equinox RC". GNP la rechazó con el mismo patrón de error — el
principio queda confirmado también en su forma más literal, no sólo en la
versión más exigente que se probó aquí.

### Caso 4 (añadido el mismo día) — verificación de la clave 37 de `cotizador-eot`: **`[CONFIRMADO]`**

Al escribir el punto 6 de ADR-005 se citó "clave 37" para el rechazo de
coberturas excluyentes, tomado de un comentario ya existente en
`app/core/Esquema.php` (línea 361-362, fechado 25-ago-2026) — pero sin ninguna
fila de `sys_llamadas` que lo respaldara. Beto lo señaló antes de dejarlo
escrito así en el ADR, con razón: nada se marca `[CONFIRMADO]` sin poder
apuntar a la llamada exacta. Se repitió la prueba para conseguirla:

Misma cotización base, Amplia (`PRS0009355`), pidiendo juntas **Auto
Sustituto** (`0000001414`, suma 20) y **Auto Sustituto Plus** (`0000001415`,
suma 20) — el par excluyente de `cat_coberturas_excluyentes`.

```xml
<ERROR>
   <DESCRIPCION>LAS COBERTURAS AUTO SUSTITUTO, AUTO SUSTITUTO PLUS Y AYUDA PARA PÉRDIDAS TOTALES SON EXCLUYENTES. FAVOR DE SELECCIONAR SÓLO UNA. (122059751)</DESCRIPCION>
   <CLAVE>37</CLAVE>
   <ORIGEN>cotizador-eot</ORIGEN>
   <FECHA>2026-09-10T14:11:56.669-06:00</FECHA>
</ERROR>
```

**`sys_llamadas.id = 62`.** El comentario de `Esquema.php` resultó exacto —
sólo le faltaba el registro en bitácora que lo hiciera citable. Evidencia en
`datos/evidencia_02.6_coberturas_modificadas/05-verificacion-excluyentes-*.txt`.

## Qué significa para el módulo

| Pregunta del ADR-007 | Respuesta |
|---|---|
| ¿Se puede mandar `<COBERTURAS>` modificado? (punto 2) | **Sí**, y tarifica de forma coherente |
| ¿Se puede salir del paquete base? (punto 3) | **No** — GNP rechaza con error claro |
| ¿El diseño de `cat_plantillas`/`cat_plantilla_coberturas` sigue siendo válido? | Sí, sin cambios: limitar las coberturas ofrecidas a las del paquete base (punto 3 del ADR-007) es correcto, no sólo prudente |
| ¿`GnpClient.php` necesita cambios? | No — el soporte para `<COBERTURAS>` con valores propios ya existía (parámetro `$opcionales` de `cotizar()`), sólo no se había ejercitado nunca |

## Algo que sorprendió

El `ORIGEN` de los errores de los Casos 2 y 3 fue **`cotizador-eot`**, que en
ese momento no aparecía en la taxonomía de
[ADR-005 punto 6](./03_Decisiones/ADR-005-reglas-verificadas-gnp.md#6-los-errores-se-clasifican-por-el-campo-origen-confirmado).
Cae correctamente en `E_DATOS` por la regla de respaldo de
`GnpClient::clasificar()` (clave ≥ 2 → datos), así que el sistema no se rompe
con esto. Ya se agregó a esa tabla (con el Caso 4 de arriba, clave 37, de
paso) — cada clave con su `sys_llamadas.id`, no de oídas.

## Pendiente que esto no resuelve

El punto 7 del ADR-007 (si `<COBERTURAS>` modificado convive con `<PAQUETES>`
múltiple en una sola llamada) sigue sin probarse: esta prueba mandó un solo
paquete por llamada a propósito, para no mezclar dos variables a la vez. Es la
siguiente prueba lógica si se quiere el comparativo "mi paquete Equinox vs. los
de GNP" en una sola llamada.
